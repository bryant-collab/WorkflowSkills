# Deliver an issue or change

Confirm the task's repository and issue acceptance criteria, including linked PRs and duplicate reports that affect scope. Read local instructions and discover the canonical repository separately from the push remote; a fork's `origin` is not proof that its issues or default branch are the intended target. Resolve the actual base branch from GitHub and repository policy. Inspect branch/worktree state and preserve unrelated changes. Use an isolated checkout when needed; do not reset or discard work to simplify delivery.

Identify the repository's required build, test, lint, and runtime checks from its configuration and contribution documentation. Reproduce a defect or capture a useful baseline when practical. Implement the smallest justified change. Use red-before-green regression proof where a meaningful test path exists; otherwise record the concrete alternative and gap. A repository-generated verification skill may help when present, but is not a prerequisite.

Run targeted checks and the appropriate repository checks. Exercise the changed user path when the claimed outcome depends on runtime behavior. Record exact commands, outcomes, environment limits, and retained proof. Review the diff for correctness, scope, sensitive content, useful comments, and affected contracts. Scale independent review to risk and the user's requested delegation; do not impose agents on a small change.

When the request authorizes PR delivery, commit only task changes on an appropriate branch, push to the verified remote, and create or update the PR in the canonical target with the verified base. Resolve an existing PR before creating a duplicate. Follow the project's title and template conventions; no universal prefix or section layout is required. Lead the body with the problem and resulting behavior, then relevant verification and limitations. Link the issue; use a closing keyword only when this PR's merge should resolve it. Keep incomplete or unverified work draft when warranted and report what remains. Do not mark an existing draft ready without authorization to complete that transition and evidence of readiness.

After every relevant push, use [PR status](pr-status.md) to refresh CI and review evidence for the current PR head. Revalidate local evidence invalidated by changes. Report the PR URL, demonstrated acceptance criteria, check results, and remaining blockers. An unavailable check or review surface is a gap, not success. Stop at the requested delivery boundary; PR creation itself does not authorize replies, review dismissal, thread resolution, merging, auto-merge, or recurring observation.

For an authorized merge-ready pass, verify each finding against the code, batch justified fixes, run affected checks, and push through the single delivery owner. Replies or thread resolution require authorization covering those actions. Do not rewrite branch topology, force-push, or retry CI blindly to obtain a green result. Classify failures using logs and base state, then make the smallest warranted repair or report the external blocker. Respect required human approval.
