# C# changes and verification

Follow the repository's actual .NET version, libraries, analyzers, and test conventions. Inspect `global.json`, solution/project files, `Directory.Build.props` or `.targets`, package management, CI, and nearby tests where present. Use the documented repository commands; inspect installed SDKs or tool help when a command or target is uncertain. Do not replace an existing test framework or update the SDK as incidental setup.

Trace the ticket's user path through entry points, domain logic, persistence, and external boundaries. For an API change, inspect serialization, validation, compatibility, and real callers. For a service or background job, inspect scope lifetimes, failure handling, cancellation, and replay behavior. For EF or another persistence layer, inspect actual query semantics, transactions, migrations, and provider-dependent behavior. Read the relevant library's current official documentation when a concrete behavior is uncertain; do not make framework claims from naming alone.

Use domain types to express real invariants, consistent with existing style. Nullable annotations help explain a contract but do not validate incoming JSON, database rows, or external responses. Keep validation at the correct boundary and preserve error contracts. Avoid broad catch-and-continue changes that hide failures. When touching async work, trace cancellation and resource lifetime rather than adding `Task.Run`, blocking waits, or retry wrappers by habit. Evaluate retries against actual side effects and idempotency constraints.

For a defect, reproduce the failing behavior with the nearest practical test before fixing it. Assert the caller-visible contract: returned values, state changes, emitted events, or meaningful errors. Use the repository's existing fixture style; avoid mocks that merely repeat the implementation. Test serialization, query translation, transactions, or concurrency at a boundary capable of demonstrating that behavior when the change depends on it. An in-memory substitute is not proof of a production provider's semantics.

Run the narrow affected tests and the repository's required build, analyzer, formatting, and broader checks appropriate to the change. Distinguish compile success, behavioral test evidence, integration evidence, and deployment evidence. State the exact target or filter and what was not exercised; do not report the entire solution passing after running one project. If services, credentials, or SDKs prevent a check, report that concrete gap and complete useful available checks. Do not access production or apply database migrations merely to obtain proof.

Map meaningful Jira acceptance criteria to the evidence produced. For example, a ticket requiring safe repeated submission needs evidence for duplicate handling at the side-effect boundary; a unit test of a key generator alone does not settle it. Keep a manual verification recipe pending until executed. Preserve approved product decisions while resolving implementation details through the engineering core.
